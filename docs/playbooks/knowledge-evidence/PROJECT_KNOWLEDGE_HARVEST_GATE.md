# Project Knowledge Harvest Gate

## Purpose

A project is not fully closed until its reusable knowledge has been extracted. Delivery produces client value; harvest converts experience into Studio Platform capability.

## Trigger

Run the gate at major milestones, after incidents and before final project closure.

## Required inputs

- accepted scope and actual outcome,
- major decisions and trade-offs,
- delivery, design, technical and commercial evidence,
- incidents, rework and surprises,
- client feedback,
- final financial and operational result.

## Mandatory questions

1. What assumption proved wrong?
2. What decision should be repeated?
3. What failure mode should become a control or test?
4. What artifact can be reused?
5. What capability can now be claimed with evidence?
6. What must remain client-confidential?
7. Which existing standard is now incomplete or obsolete?

## Required outputs

As applicable, the harvest must create or update:

- decision records,
- playbooks and gates,
- templates or checklists,
- test scenarios,
- design patterns,
- capability evidence,
- case-study material,
- pricing or sales guidance,
- risk and incident controls.

A lesson written only in a retrospective is not harvested until it changes a durable asset or an explicit decision.

## Acceptance criteria

The gate passes only when:

- an accountable harvest owner is named,
- sensitive content is classified,
- each accepted lesson has a destination,
- duplicate or contradictory guidance is resolved,
- new assets are linked and discoverable,
- capability claims reference evidence,
- remaining actions have owners and dates.

## Failure conditions

The gate fails when the team closes the project with undocumented founder knowledge, unsupported marketing claims, unresolved contradictions or lessons that exist only in chat history.
